# Model acquisition — the 30B training-target search

Four throwaway scripts from the 2026-08-31 hunt for a trainable 4-bit
Qwen3-Coder-30B. Kept because the search has a **negative** result that is
expensive to rediscover, and a script that was run is better evidence of what
was tried than a memory of it.

They carry machine paths (`/home/jarvis_svc/.venvs/reactor-train`,
`HF_HOME=/home/jarvis_svc/.cache/huggingface`) on purpose — this is a record
of what ran on this host.

| script | what it does |
|---|---|
| `findmodel.py` | HF API search for 4-bit / AWQ / GPTQ Qwen3-Coder-30B variants |
| `sizes.py` | compares file lists + sizes across the four candidate repos |
| `dl.sh` | downloads the GPTQ 4-bit mirror |
| `run30b.sh` | **DEAD — DO NOT RUN.** See below |

## The GPTQ mirror is dead twice over — do not retry it

`btbtyler09/Qwen3-Coder-30B-A3B-Instruct-gptq-4bit` (18 G) fails on
transformers 5.16.1 + gptqmodel 7.3.5 for two independent reasons:

1. **The experts do not load.** `model.layers.{0..47}.mlp.experts.down_proj` /
   `.gate_up_proj` and `mlp.gate.weight` report *MISSING → newly initialized*
   while `mlp.experts.{0..127}.*.qweight/qzeros/scales` report *UNEXPECTED*.
   The MoE expert tensors map onto nothing; training it would train randomly
   initialized experts.
2. **It dequantises anyway.** 59.38 GiB resident for a "4-bit" 30B on both the
   `torch` and `triton` backends. Observed live: the card pinned at
   32051–32081 MiB of 32607 with *The model is already on multiple devices*,
   and the profile never reached its weights-resident mark.

**`run30b.sh` (Aug 31 14:54) predates the finding that killed it (`609a620`,
Sep 1 08:17), so it is stale by construction.** Checking a script's date
against the commit that invalidated it is the cheap move that would have
saved that detour.

## What replaced it

`Qwen/Qwen3-Coder-30B-A3B-Instruct` **base bf16** (16 shards / 56.9 GiB,
downloaded 2026-09-03), with bnb-NF4 applied at load — the documented route to
a 4-bit 30B on this stack. It is also the flywheel-correct target: the corpus
was generated BY `qwen3-coder:30b`, so it is the model the corpus can teach.

`Qwen/Qwen3.8-27B` (52 G) is local too but is a DIFFERENT model — training it
would mean serving it for generation as well, which breaks the loop.

Training is driven by `scripts/run_grpo_training.py`, which gates on
`grpo_preflight.analyse` and `reactor_core/training/memory_guard.py` before
torch is imported. A soak and a training run cannot share this card — ollama
holds ~22 GB during generation. Sequence them; never profile during a soak.
